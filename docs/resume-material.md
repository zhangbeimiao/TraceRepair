# TraceRepair 简历与面试材料

## 简历项目名

**TraceRepair｜受控代码修复 Agent｜Python / SQLite / pytest / LLM Tool Calling**

## 推荐简历表述

- 设计“推理权—执行权”分离的代码修复 Agent：LLM 仅输出结构化只读工具选择与候选 Unified Diff，确定性控制器负责阶段白名单、Token/轮次预算、补丁策略和状态机调度。
- 实现补丁与执行安全门禁：路径白名单、改动规模限制、hunk 上下文唯一匹配、预登记 pytest 目标测试和完整回归；模型无任意 Shell、原仓库写入或自动合并权限。
- 基于 SQLite 持久化模型决策、工具事件、状态迁移与 Checkpoint，并用 SHA-256 校验恢复工件和工作区，实现进程重启后跳过已完成步骤的幂等恢复。
- 构建带 oracle 预检、不可覆盖 pass@1 记录和 SHA-256 哈希链的多仓库历史 Bug 评测；冻结 Agent `0.5.0` 在 3 个真实历史 Bug 上取得 **2/3 pass@1**，另 1 次在写文件前安全拒绝，**错误接受补丁数为 0**，平均输出 268.67 Tokens。

样本量只有 3 个，简历中不要写“准确率 66.67%”作为泛化结论。`2/3 pass@1` 比百分比更诚实，也更容易解释评测协议。

## 30 秒介绍

TraceRepair 是一个受控代码修复 Agent。模型负责根据 Issue 和源码观察选择搜索、读取并提出一次候选 Diff；控制器负责工具权限、补丁策略、目标测试、完整回归、Trace 和崩溃恢复。冻结的 Agent 0.5.0 在三个真实历史 Bug 上取得 2/3 pass@1，第三个任务因为补丁定位超过安全范围，在写文件前拒绝并转人工，所以错误接受补丁数是 0。这个项目重点不是包装 100% 成功率，而是让模型失败可见、可拒绝、可恢复。

## 锁定失败的 Debug 故事

More Itertools 任务中，模型生成的修改意图接近历史修复，但 Unified Diff 标注的 hunk 起点是 1098，唯一精确上下文实际位于 1185，相差 87 行。当前控制器只允许在标注位置前后 80 行内做精确、唯一的重定位，因此触发 `PATCH_CONTEXT_MISMATCH`。系统没有写源码、没有运行测试，直接进入 `needs_human`。

这次失败不能在原评测上“修好再跑”。如果未来采用函数锚点、AST 定位或更大的受控窗口，必须发布新 Agent 版本，创建新 benchmark manifest，并把成功与失败重新完整冻结。旧版 `2/3` 永久保留。

## 不要这样写

- “代码修复准确率 100%”。
- “可自动修复任意 Python 仓库”。
- “锁定集失败是模型答案正确，只是系统太严格”。候选补丁未应用、未测试，不能算成功。
- “哈希链保证报告不可篡改”。准确说法是：在终端摘要已外部发布后，链式记录和校验和可检测后续篡改；它不等于第三方不可变存储。

## 面试时展示顺序

1. 先运行 `python scripts/showcase.py --section evidence`，展示 2/3、一次安全拒绝和版本纪律。
2. 再展示一条成功 Diff 及 policy、target、regression 三层门禁。
3. 展示 `PATCH_CONTEXT_MISMATCH`，说明为什么宁可转人工也不模糊套用。
4. 最后展示补丁落盘后崩溃恢复，强调 SHA-256 校验和不重复模型调用。
