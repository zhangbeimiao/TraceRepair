# TraceRepair 0.8 development track: prompts, native functions, and code RAG

This document describes development work. It does **not** replace the frozen
`0.7.0-dev2` result: six unseen repositories, `2/6 pass@1`, four safe human
handoffs, and zero observed incorrect accepted patches.

## `0.8.0-dev1`: native Function Calling and Prompt Registry

The model no longer returns a hand-written JSON action envelope. Each request
uses provider-native function schemas with `tool_choice=required` and parallel
calls disabled. Provider schema guidance is never treated as a security
boundary: the host validates the
envelope, function name, argument names, types, ranges, path shape, current
stage, call budget, and token budget before the action reaches a tool.

| Stage | Advertised model functions | Controller-only operations |
|---|---|---|
| diagnosis | current subset of `repo_map`, `search_code`, `read_file`, plus `handoff` | all writes and tests |
| patch generation | `propose_patch`, `handoff` | patch policy and application |
| semantic review | `propose_patch`, `handoff` | target test and regression test |

`apply_patch`, `run_tests`, `run_regression`, and state transitions never appear
in the model tool schema. A valid function call therefore remains a proposal,
not execution authority.

`src/tracerepair/prompt_registry.py` versions three prompts independently. A
prompt hash covers the stage, system text, user template, and evidence encoding.
Repository evidence is clipped, placed in the user message, labelled untrusted,
and has delimiter tokens escaped. Every model decision persists:

- prompt ID and SHA-256;
- advertised tool-schema SHA-256;
- stage and selected function;
- argument SHA-256 and tool-call-ID SHA-256;
- policy acceptance or sanitized parse error;
- completion tokens and budget checkpoint.

The complete development contract is generated and verified without an API
request:

```powershell
python scripts\freeze_protocol_manifest.py
python scripts\freeze_protocol_manifest.py --verify
```

The generated file is
`evaluation/protocols/native-function-calling-v0.8.0-dev1.json` with an adjacent
SHA-256 file. It is a protocol contract, not a repair-rate result.

The deterministic injection suite covers delimiter closure, secret requests,
unknown functions, path traversal, diagnosis-to-patch stage jumps, regex/command
chaining, and parallel calls. All `6/6` host-boundary cases are contained and
the report is hashed at
`evaluation/results/prompt-security-v0.8.0-dev1/report.json`. This verifies the
controller contract; it does not claim that an LLM resists every injection.

### Protocol comparison

The candidate uses exactly the same five known development tasks as the
`0.7.0-dev2` JSON-planner development report. After one native run, the paired
comparison separates format-contract failures from patches rejected by tests:

```powershell
python scripts\run_benchmark.py `
  --manifest evaluation\benchmarks\function-calling-v0.8.0-dev1.json `
  --split development
python scripts\compare_planner_protocols.py
```

No locked task belongs to this benchmark. A lower format-failure rate here is a
development-set protocol result, not evidence of broad code-repair accuracy.

The first online run is retained as negative evidence: `0/5 pass@1`, with all
five attempts stopped by the Function Calling format contract. Diagnosis tools
were successfully selected, but four patch/review calls supplied an invalid
`reason` value and one patch call used an unknown function name. The next
compatibility revision must use a new Agent version, Prompt/Schema hashes, and
benchmark ID; this result is not rerun or overwritten.

### `0.8.0-dev1.1`: narrow provider-compatibility revision

The compatibility revision is versioned separately and keeps the `0/5` parent
ledger immutable. It makes `reason` optional audit metadata rather than an
authorization field and accepts one narrowly scoped provider alias:
`apply_patch(patch=...)` is normalized to `propose_patch(unified_diff=...)` only
while the controller is already in the patch stage. The alias does not apply a
patch. It cannot write files, start tests, transition state, or bypass any Diff,
path, target-test, or regression gate. The trace records both the provider name
and canonical name plus a compatibility-normalized flag.

The versioned contract and deterministic security evidence are:

- `evaluation/protocols/native-function-calling-v0.8.0-dev1.1.json`;
- `evaluation/results/prompt-security-v0.8.0-dev1.1/report.json`;
- `evaluation/benchmarks/function-calling-v0.8.0-dev1.1.json`.

The security suite includes an explicit attempt to use the compatibility alias
during diagnosis; the host rejects it before any write or test. The same five
known development tasks may be used to measure whether this protocol revision
fixes format failures. No locked task is available to this version yet.

## `0.8.0-dev2`: bounded code RAG

The retrieval layer is optional and read-only:

1. Allowlisted Python files are split by AST function/class boundaries; large
   symbols are windowed with bounded overlap.
2. Chunk text, symbol, line range, and SHA-256 are stored in a local SQLite
   database on D:.
3. SQLite FTS5 supplies lexical candidates.
4. The frozen embedding model supplies vector candidates.
5. Reciprocal Rank Fusion combines ranks; raw score scales are never mixed.
6. Top candidates are labelled untrusted and added to diagnosis evidence.
7. The model must still call `read_file`; retrieval cannot write, test, or
   transition task state.

The planned semantic configuration is `qwen3.7-text-embedding-flash`, 256
dimensions, Top‑5, and RRF `k=60`. These values are included in
`evaluation/benchmarks/code-rag-v0.8.0-dev2.json`, so changing any one produces
a new manifest hash. Alibaba Cloud documents an OpenAI-compatible Embedding API
and supports 256-dimensional output for this model.

### Retrieval evaluation

Ground truth contains the historically changed source file for five known
development tasks. The query contract is only the issue plus failing pytest
selector; hand-written diagnostic queries are excluded. Reports contain
file-level Recall@1/3/5, MRR, repository fingerprint, chunker version, model,
dimensions, and a SHA-256 sidecar.

Offline results already recorded:

| Retriever | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---:|---:|---:|---:|
| SQLite FTS5 | 0.60 | 0.80 | 1.00 | 0.7500 |
| Local hash-vector path test + RRF | 0.40 | 0.80 | 1.00 | 0.5833 |

The local hash vector is explicitly **not** a semantic embedding model. Because
it worsened ranking, it is retained as negative evidence and is not enabled in
the Agent. The semantic candidate is activated only if it preserves Recall@5
and improves Recall@1 or MRR over FTS5:

```powershell
python scripts\evaluate_retrieval.py --embedding bailian
python scripts\evaluate_retrieval_gate.py
```

The second command verifies both report checksums and the frozen model and
dimension settings, then emits a hashed activation decision. A failed gate keeps
RAG disabled and exits non-zero; it does not silently promote `dev2`.

The first Bailian embedding run preserved Recall@5 but exactly tied FTS5 on
Recall@1 and MRR (`0.60` and `0.75`). The frozen decision is therefore
`keep_rag_disabled`. This is a valid negative result, not an infrastructure
failure.

### `0.8.0-dev2.1`: file-level fusion candidate

The tied `dev2` result remains unchanged. A separate candidate addresses a
metric/implementation mismatch: the old RRF fused AST chunks while evaluation
ranked unique files, allowing multiple chunks from one large file to crowd out
other files. `dev2.1` first collapses lexical and vector results to unique file
ranks, then performs RRF and chooses one representative chunk per file. It also
reports vector-only Recall@K/MRR so a hybrid improvement can be attributed
rather than inferred.

Index construction now reuses embeddings only when repository fingerprint,
chunker, allowlisted roots, model, dimensions, and stored row counts all match.
This avoids paying to embed unchanged code while failing closed on stale or
partial indexes. The candidate remains retrieval-only until its new activation
gate passes; it has no write, test, state-transition, or execution authority.

The registered run passed that gate: file Recall@3 improved from `0.80` to
`1.00`, MRR improved from `0.75` to `0.80`, and Recall@5 remained `1.00`.
Vector-only retrieval also reached Recall@3/5 `1.00/1.00` and MRR `0.80`, so
the improvement is attributable to semantic ranking rather than an FTS-only
artifact.

The one-pass repair evaluation on the same five known tasks is now frozen. It
achieved `3/5 pass@1`, equal to the no-RAG native-functions parent, with two
safe handoffs and zero incorrect accepted patches. Average completion tokens
fell from `489.6` to `473.6`; P95 wall time fell from `51.234s` to `18.906s`.
These are descriptive development measurements, not a repair-rate or latency
generalisation claim.

The failures expose two different boundaries. For tqdm, retrieval found the
right file but the selected source slice still omitted `__bool__`, so the model
handed off. For HTTPie, retrieval ranked the exact target symbol first, but the
model emitted a malformed unified-diff hunk header. The deterministic parser
returned `PATCH_PARSE_ERROR`; no file write or test occurred. The exact trace
candidate, public text copy, logs, report, comparison, and checksums are stored
under `evaluation/results/rag-repair-v0.8.0-dev2.1/`.

The five development tasks will not be rerun under this version. The Agent can
enter a locked benchmark only after the complete prompt, function schemas,
retrieval configuration, model, task manifests, and oracles are frozen.

## `0.8.0`: release gate

The release requires all of the following:

- all unit, injection, recovery, and frozen-evidence verification tests pass;
- native Function Calling has a published paired development comparison;
- semantic RAG has a published Recall@K/MRR report and beats its activation
  gate;
- development tuning stops before new locked repositories are selected;
- at least three previously unused repositories are pre-registered with valid
  buggy/fixed oracle checks;
- each locked task runs once; every success and failure is published;
- zero patch may be accepted without target and regression success;
- the old `0.7.0-dev2` reports and hashes continue to verify byte-for-byte.

Until these conditions are met, the honest public wording is: “0.8 Function
Calling and Code RAG development evidence frozen; locked generalisation
evaluation pending.”

## One-command online development run

After the two Bailian environment variables are configured in the same
PowerShell session, the following command runs only the known development
protocols. It never selects a locked task:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\run_v080_development.ps1
```

The command is restart-safe at the benchmark level: an already recorded pass@1
task is not rerun. Use `-SkipFunctionBenchmark` or `-SkipRetrieval` to resume
only the missing half.
