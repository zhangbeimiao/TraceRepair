# TraceRepair 三分钟面试讲稿

这份讲稿按正常语速约三分钟。重点不是背 Agent 定义，而是讲清楚为什么
这样设计、模型出错时系统如何兜底，以及结果如何被验证。

## 0:00–0:25｜项目背景

> 我做的项目叫 TraceRepair，是一个面向受信任小型 Python 仓库的代码修复
> Agent。输入是 Issue、失败测试和仓库配置，输出不是直接合并代码，而是一个
> 经过策略校验、目标测试和完整回归测试的候选补丁，最终仍然需要人工审核。
> 我做这个项目的重点不是让模型演示一次“写对代码”，而是研究模型判断错误、
> 工具失败或者进程中断时，系统怎样安全停止和恢复。

## 0:25–0:55｜为什么使用 Agent

> 如果 Bug 所在文件和修改步骤都是已知的，固定工作流就足够了。但代码修复中，
> 系统事先不知道应该搜索什么符号、读取哪个文件，也不知道已有证据是否足够生成
> 补丁，所以我让模型负责这些依赖观察结果的不确定决策。与此同时，我没有让模型
> 直接写文件或运行 Shell，而是把执行权留给确定性控制器。这就是项目里 Agent
> 和普通大模型 API 调用的主要区别。

## 0:55–1:35｜核心架构

> 整体分成三层。第一层是模型规划器，使用百炼的 qwen3.8-flash，只能返回结构化
> 的工具选择或者一个 unified diff。第二层是确定性控制器，它维护状态机、阶段、
> Token 和调用预算，并校验工具名和参数。第三层是执行与验证层：只读阶段只有
> repo_map、search_code 和 read_file；补丁必须通过路径白名单、变更体积和上下文
> 唯一性校验，之后写入一次性工作副本，再依次执行预先登记的目标测试和回归测试。
> 全部通过也只进入 awaiting_review，模型没有权限宣布自动合并。

## 1:35–2:10｜真实故障与 Debug

> 项目早期并不是一直成功。模型出现过只在错误文件中反复搜索、诊断轮次耗尽、
> 返回非法结构，以及 Diff 上下文和源码不匹配等问题。以
> PATCH_CONTEXT_MISMATCH 为例，如果直接尝试模糊套用补丁，可能会改错位置。
> 我的处理方式是把模型输出当成不可信候选：补丁上下文必须唯一匹配，否则不写入
> 文件，也不启动测试，任务直接转 needs_human。对于模型搜索偏离的问题，我加入了
> 阶段化工具白名单和确定性恢复步骤，让控制器补充必要的搜索和读取，但恢复过程仍然
> 受轮次和 Token 上限约束。

## 2:10–2:35｜Trace 与崩溃恢复

> 为了能够定位这些问题，我把模型决策、工具开始和结束、状态迁移以及 checkpoint
> 全部写进 SQLite。进程重启时会读取 checkpoint，并校验相关文件的 SHA-256，只有
> 工件没有被外部修改才会跳过已完成步骤。例如补丁已经落盘后进程崩溃，恢复阶段
> 不再调用模型，也不会重复应用 Diff，只继续运行目标测试和回归测试。这个场景有
> 独立的两阶段进程测试，不只是内存中的异常模拟。

## 2:35–3:00｜效果与边界

> 最终我冻结了 Agent 0.6.0，并在五个不同开源仓库的历史 Bug 上按 pass@1 评测。
> 三个开发任务只用于调试，结果是 2/3；随后冻结 Prompt、预算和策略，再对 HTTPie
> 与 youtube-dl 两个全新锁定仓库各运行一次，结果是 1/2。完整结果为 3/5 pass@1，
> 两个失败候选都被目标测试拦截并转人工，0 个错误补丁被接受，平均输出 273.8
> Tokens。Wilson 95% 区间是 23.07% 到 88.24%，所以我只把它作为真实闭环和安全
> 拒绝的证据，不能声称广泛泛化能力。旧版 0.5.0 的 2/3 仍保留，但题集不同，不能把
> 两个百分比当成直接精度对比。EventRelay 13/13 和第二仓库 5/5 只作为工程回归证据。

> 此后状态机迁移到 LangGraph，SQLite 仍是唯一持久化源，补丁复核没有执行权。
> 五个已知开发任务从 2/5 提升到 4/5，错误接受仍为 0；平均 Token 从 315.6
> 增至 543.2，P50 从 9.985 增至 14.329 秒。这只证明已知任务收益，
> 不能当作盲测。

## 演示时的操作顺序

先用一条命令展示完整闭环：

```powershell

```

如果面试官追问某个技术点，再只展示对应部分：

```powershell
python scripts\showcase.py --section failure
python scripts\showcase.py --section recovery
python scripts\showcase.py --section repair --case 10
```

最后打开在线 Demo 查看真实 Diff、验证门禁和冻结指标：
<https://zhangbeimiao.github.io/TraceRepair/>。

## 容易被追问的四个点

1. **为什么不用固定工作流？** 搜索和读取路径依赖前一步观察；执行与验证仍然是固定门禁。
2. **为什么不用模型直接改文件？** 模型输出不可审计且可能越权；候选 Diff 更容易校验、回放和拒绝。
3. **测试通过是否等于修复正确？** 不等于，所以保留完整回归、Diff 审核和 `awaiting_review` 人工门禁。
4. **最大的不足是什么？** 当前只执行受信任仓库；pytest 仍会运行仓库代码，未知代码需要容器或 VM 沙箱。

## 30 秒压缩版

> TraceRepair 是一个受控代码修复 Agent。模型只负责选择搜索、读取工具并提出一次
> 候选 Diff；确定性控制器负责权限、预算、补丁策略、目标测试、完整回归、SQLite
> Trace 和 Checkpoint 恢复。模型不能运行任意 Shell，也不能直接写原仓库或自动
> 合并。冻结的 Agent 0.6.0 在五个真实历史 Bug 上取得 3/5 pass@1，两个失败候选
> 都被目标测试拒绝并转人工，错误接受补丁数为 0。我更关注模型
> 失败时如何安全停止、定位和恢复，而不是只展示一次成功 Demo。新的 LangGraph
> 开发版在相同已知任务上从 2/5 提升到 4/5，但我明确把它标为开发证据，等待全新
> 锁定仓库验证。

## 版本与评测纪律

`historical-python-v1.1.3` 的 Agent、Prompt、补丁策略、五次结果和终端哈希已经冻结。
如果未来放宽补丁定位或增加更可靠的结构化定位算法，必须提升 Agent 版本、复制成新的
benchmark manifest，并使用全新锁定仓库；不能重跑失败样本后覆盖本次 `3/5`。
`langgraph-review-offline-v0.7.0-dev2` 的 `4/5` 也已冻结为开发证据；任何针对 tqdm
失败的策略调整都必须升级为新 Agent 版本，不能覆盖本次结果。
